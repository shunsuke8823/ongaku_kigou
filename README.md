# かたちではっけん！ おんがくきごう♪

## 1. サービス概要

ピアノ練習中に分からない音楽記号が出てきたとき、子どもが**記号の見た目(形)から**意味を調べられるWebアプリ。
「分からない!」をその場で「分かった!」に変え、練習に集中できるようにする。

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

子どもの頃にピアノを習っていたが、楽譜の記号の意味が分からず、週1回のレッスンで先生に聞くしかなかった。それ以外の日は、分からないまま練習を続けていた。

### 2-2. なぜそれが「気になった」のか

当時は自分で調べる手段がなかった。しかし、仮にスマートフォンがあっても、記号の名前が分からなければどうやって検索すればいいか分からない。

→「調べる道具」があっても「調べる入口」がないことが気になった。

## 3. 課題の整理

### 3-1. 表に見えている困りごと

楽譜の音楽記号の意味が分からず、そのままになっている。

### 3-2. 本当に解決したい課題は何か

- なぜ意味が分からないままなのか?
  → 先生に聞けるのが、週1回のレッスンのときだけだから。
- なぜレッスン以外の日に自分で調べないのか?
  → 記号の名前が分からず、どうやって検索すればいいか分からないから。
- なぜ名前が分からないと調べられないのか?
  → 辞典や検索は名前(文字)から調べる作りで、見た目(形)から探す入口がないから。

**本当に解決したい課題:** 先生に聞けないときに、名前の分からない記号を自分で調べる手段がないこと。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

**週1回ほどピアノを習っている小学生**

- 理由:ピアノを習い始める子が多く、音楽記号に一番苦戦する年齢だと考えるため。
- 懸念:小学生はスマートフォンを持っていない、検索が難しい、フィルタリングで検索できない、といったことが多い。  

  → MVPでは、**実際に使うのは子ども、見つけて導入するのは保護者**と想定する。

### 4-2. 自分とユーザーの距離

子どもの頃の自分そのものであり、同じ困りごとを実際に体験している。

### 4-3. 実際に使われる可能性について(需要・存在確認)

- ビデオリサーチの調査(2025年10月)では、女子小学生の人気の習い事1位が「ピアノ」であり、今もピアノを習う子どもは多い。
- 子ども向けの音楽記号クイズアプリや、ふりがな付きの楽典本があり、「子どもが音楽記号を学ぶ」需要はある。
- ただし、その多くは名前が分かっている前提の作りで、見た目から探せる子ども向けのアプリ・Webサービスは見当たらない。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)

1. 子どもに楽譜の記号について聞かれた保護者が、検索してこのサービスを見つける。
2. 保護者のスマートフォン・タブレットのホーム画面に追加する。
3. 子どもが家での練習中に形をタップして調べ、意味と音を確かめて練習を続ける。
4. 次のレッスンで、先生に「合ってた?」と確認する。
5. 分からない記号が出てくるたびに、このアプリで調べるようになる。

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

| 名前 | 種類 | できること |
| --- | --- | --- |
| [音楽用語辞典](https://apps.apple.com/jp/app/音楽用語辞典/id1470912398) | スマートフォンアプリ | 8000語以上を収録。文字検索、楽譜を撮影してAIが認識 |
| [ジュニア版 ありそうでなかった 形から引ける音楽記号辞典](https://amzn.asia/d/0grmTT94) | 書籍 | 形から記号を探せる。ふりがな・イラスト付き |

### 5-2. それでも自分が作りたい理由

- **音楽用語辞典**
  - 最新のAndroid端末では使えず、最終更新も2023年12月で止まっている。
  - 文字が小さく大人向けの作りで、小学生がひとりで使うのは難しい。
  - 楽譜を撮影しての認識は、試したところ正確に認識されないことが多かった。
- **ジュニア版 ありそうでなかった 形から引ける音楽記号辞典**
  - 紙の本のため、ページをめくって探す手間がかかり、持ち歩きにくい。
  - 記号によってどう変わるかを、音で確かめられない。

### 5-3. 差別化を「体験価値」で表現する

- 保護者のスマートフォンでもタブレットでも、ブラウザで開くだけですぐ使える。
- 大きな文字とボタンで、小学生がひとりでも迷わず操作できる。
- 形をタップしていくと、クイズ感覚で記号にたどり着ける。
- 意味を読むだけでなく、音を聞いて違いが分かる。

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

次のレッスンを待たずに、その場で記号を自分で調べて意味が分かることで、集中を切らさずに練習を続けられる

### 6-2. 価値を一文で表す

**ピアノを習う子どもが、先生のいない日でも、名前を知らない音楽記号を「形」から自分で調べられるサービス**

## 7. このアプリで実現すること

### MVPで作る機能

| 機能 | 内容 | 必要な理由 |
| --- | --- | --- |
| 形から逆引き | 「点」「線」「文字」「曲線」などの特徴をタップして絞り込む | 名前が分からなくても探せる、中心となる機能 |
| 記号の詳細ページ | 画像・読み方(ふりがな付き)・意味・弾き方のポイント | ベースとなる機能 |
| 一覧・カテゴリ表示 | 強弱・速さ・弾き方などのグループで表示 | 逆引きで見つからないときのため |
| 名前検索 | ひらがな(「すたっかーと」など)でも検索できる | 名前を知っている場合のため |
| 音の聞き比べ | スタッカート/レガート、p/fなど一部の記号のみ | 文字だけでは伝わりにくい違いを伝えるため |
| 子ども向けの見やすさ | 大きな文字とボタン、スマートフォン・タブレット対応 | 小学生がひとりで使えるようにするため |

- 形から逆引きする機能は、次の仕組みで実装する予定。

  - データ:記号と特徴は多対多の関係なので、記号テーブル・特徴テーブル・中間テーブルの3つのテーブルで管理する。
  - 絞り込み:特徴を1つずつ選んでいき、選んだ特徴をすべて持つ記号を表示する。タップするたびに候補が絞られ、クイズ感覚で記号にたどり着けるようにするため。
  - 画面:特徴のボタンを押すと、Turbo Framesで結果部分だけを更新する。選んだ特徴のIDはURLのクエリパラメータにまとめて持たせ、再読み込みでも選択状態が消えないようにする。
  - 0件のとき:結果の部分に「見つからなかった」ことを表示し、直前に選んだ特徴を外すボタンと、一覧ページへ移動するボタンを置く。

- 収録記号は、MVP時点で50個を目標とする。
- 子どもの個人情報を扱わないようにするため、ログイン機能・広告・外部サイトへのリンクは置かない。
- 音の聞き比べは、開発が遅れた場合は本リリースに回す。

### 本リリースで作る機能

- 記号クイズ(知識の定着を確認するため)
- お気に入り・最近見た記号(ログインなしで端末に保存)
- 「まちがいを教えて」報告ボタン(下記懸念点①参照)
- 音の聞き比べを全記号に拡大
- 収録記号を100個以上に増やす

## 8. このアプリの懸念点とその対策

### 懸念点①:記号の意味の誤り

- 何が問題になりそうか:記号の意味を間違えて載せてしまう。
- なぜそう思うか:音楽記号は外国由来で、訳し方の違いや信頼性の低い情報が混ざりやすいから。
- そのために考えている対策:
  - ネット検索だけに頼らず、信頼できる出版社の音楽記号辞典など、2つ以上の資料で確認してから登録する。
  - 参考にした資料を記号ごとにDBへ記録し、あとから確認・修正しやすくする。
  - 「正式な意味」と「子ども向けの説明」を別の項目で持ち、言い換えで意味がずれていないか見比べられるようにする。
  - 本リリースで「まちがいを教えて」ボタンを設け、報告を受け付ける。

### 懸念点②:音の違いが分かりにくい

- 何が問題になりそうか:音の聞き比べで違いが分かりにくい。
- なぜそう思うか:記号によっては、音の違いがはっきり出ないものもあるから。
- そのために考えている対策:
  - 違いがはっきり出る組(スタッカート/レガート、p/f、アクセントあり/なし)に絞る。
  - 同じ短いメロディで、「記号なし」と「記号あり」を並べて聞かせる。
  - 音だけに頼らず、音の長さ・大きさを棒の長さ・太さでも表示する。

### 懸念点③:記号が表示されない

- 何が問題になりそうか:端末によって、記号が正しく表示されない。
- なぜそう思うか:Unicodeの音楽記号は、端末によって表示されない場合があるから。
- そのために考えている対策:
  - 開発初期にAndroid・iPhone・iPadで表示を確認し、表示されない記号はSVG画像で用意する(拡大しても粗くならず、画面サイズが違ってもきれいに表示できるため)。

### 懸念点④：子どもと大人で特徴の捉え方が違う

- 何が問題になりそうか:アプリで決めた特徴の分け方が子どもの見え方とずれていて、目的の記号を探せない。
- なぜそう思うか:子どもと大人では、音楽記号のどこに注目するかが違う可能性があるから。
- そのために考えている対策:
  - 開発初期（記号データを全部入れる前）に、身近な子ども（親戚など）に実際に探してもらい、迷ったところを記録して特徴の分け方を見直す。
  - 1つの記号に複数の特徴を設定し、見え方が違っても見つかるようにする。

## 9. 今後の展開・発展の方向性

### 観点

- MVPでは保護者が導入する想定だが、将来は子どもが自分で見つけて、自分で使えるサービスにしたい。
- 練習中にすぐ開けるよう、通信環境に左右されず、オフラインでも使えるようにしたい。

### 今考えている発展案

- 子どもが使いそうな言葉(「がくふ きごう いみ」など)で、検索結果に出てくるようにする。
- PWAに対応し、オフラインでも検索できるようにする。

## 10. 技術スタック

### 10-1. 使用予定の技術

- 開発環境:Docker
- フレームワーク:Ruby on Rails
- DB:PostgreSQL
- CSS:Tailwind CSS
- デプロイ先:Render + Neon
- ライブラリ:Hotwire(Turbo / Stimulus)、Tone.js

### 10-2. 技術選定の比較検討

次の3つの軸で比較して選んだ。

1. **学習済みか、学習コストが低いか**
2. **このアプリに必要な機能を実現できるか**
3. **MVPの段階で無料で運用できるか**

#### フロントエンド(画面の動き)

必要な画面の動き(タップでの絞り込み、音の再生、スマートフォン・タブレット対応、PWA対応)は、どの候補でも実現できる。そのため、**学習コストの低さと構成のシンプルさ**で選んだ。

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Rails(Hotwire) | 採用 | 学習済みのRailsだけで完結し、構成がシンプル。絞り込みはTurbo Frames、音の再生はStimulusからTone.jsを呼び出して実現できる。 |
| Rails(API)+ React | 不採用 | 未学習で学習コストが高く、API連携で構成も複雑になる。 |
| Rails(API)+ Vue | 不採用 | Reactと同様に、未学習で構成も複雑になる。 |
| Rails(API)+ Next.js | 不採用 | Reactの知識も前提となり、学習コストがさらに高い。 |

#### CSS

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Tailwind CSS | 採用 | 細かい指定を組み合わせて自由に見た目を作れるため、子ども向けの大きなボタンなどを作りやすい。画面サイズごとの切り替えも簡単に書ける。 |
| Bootstrap | 不採用 | 部品がそろっていて早く作れるが、標準の見た目が大人向けで、子ども向けに上書きする手間が増える。 |

#### バックエンド(サーバー側)

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Ruby on Rails | 採用 | Docker環境で学習済みで、すぐに開発に入れる。DBのデータを画面に表示するアプリに向いている。 |
| Laravel(PHP) | 不採用 | PHPから学ぶ必要があり、学習コストが高い。 |
| Express(Node.js) | 不採用 | JavaScriptは学習済みだが、サーバー側の開発は未経験。DB接続や構成を自分で選んで組む必要がある。 |

#### デプロイ先

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Render + Neon | 採用 | 無料枠で運用でき、この構成でのデプロイ経験もある。 |
| Vercel | 不採用 | フロントエンド向けのサービスで、Railsアプリの公開には向かない。 |
| Fly.io | 不採用 | 無料で使える期間が短く、MVP期間を無料で運用するのが難しい。 |

#### DB

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| PostgreSQL | 採用 | Neonで使えるDBのため、Render + Neonの構成のまま使える。 |
| MySQL | 不採用 | Neonでは使えず、DBだけ別のサービスを追加する必要がある。 |

#### 音の再生

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Tone.js | 採用 | プログラムで音を作るため、音の長さ・強さ・速さを記号ごとに自由に変えられる。 |
| 録音した音声ファイル | 不採用 | 記号ごとにファイルが必要でデータ量が増える。目的に合った音源を探すのも大変。 |

#### 今回チャレンジしたい点

- Hotwire(Turbo / Stimulus)を使い、ページを再読み込みせずに、形を選んで記号を絞り込む。
- Tone.jsを使い、同じメロディで「記号なし」と「記号あり」の音を鳴らし分ける。
- 小学生がスマートフォン・タブレットで迷わず操作できるよう、画面サイズに合わせて表示が変わるデザインにする。

#### 不安な点

- **Hotwireでの絞り込み**:コメントをページ更新なしで反映する実装は経験したが、複数の特徴を組み合わせて絞り込む実装は初めてで、選択状態の保ち方の設計に不安がある。
- **Tone.jsでの音の鳴らし分け**:未経験のため、実装が遅れる不安がある。また、スマートフォンはタップするまで音を鳴らせず、iPhoneはマナーモードで音が出ない場合があるなど、端末による違いにも不安がある。
- **画面サイズに合わせたデザイン**:Tailwind CSSは未経験で、画面サイズへの対応も文字の大きさを変えた程度の経験しかない。スマートフォンとタブレットでボタンの並びを変える設計や、小学生が迷わないボタンの大きさの基準に不安がある。

### 10-3. キャッチアップ不足の懸念

- **Tone.js(未経験)**:学習・実装に時間がかかる懸念がある。
  - 対策:開発の最初に「ボタンを押すと音が鳴るだけ」の試作をし、実現できるかを確かめる。実装が困難であれば聞き比べを本リリースに回し、MVPでは棒の長さ・太さで違いを表示する。
 
- **Tailwind CSS(未経験)**:学習・実装に時間がかかる懸念がある。
  - 対策:一度Tailwind CSSを使用してミニアプリを作成し、どのような使用感かを確認する。
